# DataEase 后端性能优化需求文档

**日期**: 2026-04-08
**状态**: 草案
**范围**: Java 后端性能与内存优化（不更换语言）

## 背景

DataEase 后端基于 Spring Boot 3.3 + Java 21，当前在生产环境中存在内存占用偏高和性能瓶颈的问题。经过代码审查发现多项可优化空间，且均不需要更换编程语言。

### 代码库规模参考

- 后端 Java 文件: 417 个 (~55,000 行)
- SDK 共享代码: 649 个文件 (~27,000 行)
- API 端点: ~75 个
- 业务模块: 30 个（chart、dataset、datasource、permissions 等）

## 问题分析

### 当前发现的问题

1. **虚拟线程未启用** — Java 21 核心特性，平台线程每个占用 ~1MB 栈空间，虚拟线程几乎零开销
2. **GC 未优化** — 默认 G1GC 在大堆场景下停顿时间较长
3. **Ehcache 配置冗余** — 16 个缓存每个分配 10MB offheap + token 缓存 200MB 磁盘写入
4. **Tomcat 超时偏长** — 70 秒连接超时可能积压大量空闲线程
5. **JVM 参数未调优** — 未发现自定义堆大小、元空间等参数
6. **数据库连接池未显式配置** — 使用默认值可能导致空闲连接过多

## 优化方案

### P0: 启用虚拟线程（收益最大，改动最小）

**目标**: 将 Tomcat 请求处理线程和异步任务切换为 Java 21 虚拟线程

**做法**:
- `application.yml` 添加 `spring.threads.virtual.enabled: true`
- 虚拟线程使每个并发请求的内存从 ~1MB 降至 ~KB 级别

**预期收益**:
- 并发能力提升 5-10x
- 线程相关内存降低 80%+
- 无需改动任何业务代码

**风险**: 低。Spring Boot 3.3 原生支持虚拟线程。

### P1: 切换到 ZGC 垃圾收集器

**目标**: 消除 GC 停顿对请求延迟的影响

**做法**:
- JVM 启动参数添加 `-XX:+UseZGC -XX:+ZGenerational`
- 设置合理的堆大小上限

**预期收益**:
- GC 停顿从 10-50ms 降至 < 1ms
- 大堆场景下性能更稳定

**风险**: 低。ZGC 在 Java 21 中已生产就绪。

### P2: 调整 JVM 内存参数

**目标**: 避免默认配置导致的内存浪费

**做法**:
- 设置初始堆 `-Xms` 和最大堆 `-Xmx`（建议相同，避免动态调整开销）
- 调整元空间大小 `-XX:MaxMetaspaceSize`
- 启用 String 去重 `-XX:+UseStringDeduction`

**预期收益**: 总内存占用降低 30-50%

**风险**: 低。需要根据实际负载调整数值。

### P3: 优化 Ehcache 配置

**目标**: 减少不必要的内存分配和磁盘 I/O

**做法**:
- 评估各缓存的实际使用量，将 offheap 从统一 10MB 调整为按需分配
- token 缓存考虑减少磁盘持久化大小（200MB -> 50MB）或改用 Redis
- 设置合理的 TTL 替代 `<none/>`（永不过期）

**预期收益**: 减少 50-100MB 内存占用，减少磁盘 I/O

**风险**: 中。需要先监控各缓存的实际命中率。

### P4: 数据库连接池优化

**目标**: 减少空闲连接的资源占用

**做法**:
- 显式配置连接池参数（最大连接数、最小空闲、超时时间）
- 启用连接泄露检测

**预期收益**: 减少数据库连接数，降低内存和数据库负载

**风险**: 低。

### P5: SQL 与数据查询优化

**目标**: 解决 BI 工具最常见的性能瓶颈

**做法**:
- 启用 MyBatis-Plus 慢查询日志
- 分析并优化 N+1 查询
- 对高频查询添加适当的数据库索引
- 考虑大数据集查询的分页/流式处理

**预期收益**: 查询性能提升 2-10x（取决于当前瓶颈）

**风险**: 中。需要逐个分析慢查询。

## 非目标

- 不更换编程语言（Rust/Go 等）
- 不改变整体架构（不拆分为微服务）
- 不升级 Spring Boot 主版本
- 不涉及前端性能优化

## 成功指标

- 后端内存占用降低 30% 以上（从当前基线）
- P95 API 响应延迟降低 20% 以上
- GC 停顿 < 5ms
- 并发承载能力提升 3x 以上

## 实施顺序建议

1. **P0 (1天)**: 启用虚拟线程 — 改 1 行配置，立即见效
2. **P1+P2 (1天)**: JVM 参数调优 — 加启动脚本参数
3. **P3 (2-3天)**: Ehcache 优化 — 需要先监控缓存使用情况
4. **P4 (1天)**: 连接池配置
5. **P5 (持续)**: SQL 优化 — 需要结合实际使用数据
